# DEC-0017 — Repository protection includes a controlled infrastructure break-glass path

- Status: Accepted
- Date: 2026-08-26
- Context: The Foundation source repository requires `validate` and `registry-integrity` before merge. During a GitHub Actions service disruption this made `origin/main` unavailable not only for code integration but also for durable coordination between humans and AI agents. Integrity controls had become an availability single point of failure. At the same time, a bypass that can ignore a genuine red validation result would materially weaken the protection model.
- Decision: Repository protection distinguishes `VALIDATION_FAILURE`, `INFRASTRUCTURE_UNAVAILABLE`, and `UNKNOWN`. Only `INFRASTRUCTURE_UNAVAILABLE` may use break-glass. The Foundation source migrates from one classic branch-protection rule to two layered GitHub branch Rulesets: `foundation-main-core-safety` has no bypass and permanently requires PR-based change, linear history, no force push, and no deletion; `foundation-main-ci-gates` requires strict `validate` and `registry-integrity` checks and grants the authorized maintainer bypass **for pull requests only**. Direct push remains prohibited during break-glass. The PR must record outage evidence, local/manual validation, residual risk, and deferred validation. Missing checks are rerun after service recovery; a later failure creates corrective/incident work. Target projects receive the semantic policy/recommendation but Foundation transfer never silently creates bypass permissions or repository administration settings.
- Rationale: This preserves the durable repository as an available coordination channel during external CI outages without treating known validation failures as acceptable. Layered Rulesets separate controls that must never be bypassed from CI gates whose execution service can be unavailable. Pull-request-only bypass preserves review/audit history and prevents the break-glass actor from gaining a general direct-push path.
- Alternatives: keep strict classic branch protection with no bypass — rejected because GitHub Actions becomes an availability single point of failure; disable protection during incidents — rejected because it removes unrelated safeguards and creates an unaudited configuration transition; allow administrators to bypass all classic protection — rejected because it also enables direct pushes and bypasses core branch safety; synthesize successful checks — rejected because it falsifies validation evidence; automatically bypass failed checks after a timeout — rejected because project failures can also time out and infrastructure classification must be explicit.
- Consequences: `REPOSITORY_CONTINUITY_POLICY.md` becomes transferable Foundation governance; source operations are documented in `Documentation/Quality/GITHUB_BREAK_GLASS.md`; `tools/github/configure_rulesets.py` can migrate/verify source GitHub administration with an Administration-write token; normal CI remains mandatory; break-glass events carry deferred-validation debt until post-recovery checks run successfully.
- Affected areas: Foundation source GitHub administration, merge protection, validation/status semantics, direct AI transfer, target hardening recommendations, agent coordination continuity, project status/handover.
