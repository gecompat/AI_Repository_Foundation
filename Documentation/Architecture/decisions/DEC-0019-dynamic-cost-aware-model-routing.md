# DEC-0019 — Dynamic model routing optimizes fresh expected cost of success through transport-neutral contracts

- Status: Accepted
- Date: 2026-09-07
- Context: The Foundation already defines portable `LOCAL`, `ECONOMICAL`, `BALANCED`, and `FRONTIER` semantics, but concrete clients still need a consistent way to select changing provider/model offerings. Token prices, price windows, availability, context limits, quality evidence, and account constraints are runtime facts. MCP is useful in some clients but unavailable in others. Selecting only the cheapest token ignores failure/retry cost, output volume, latency, validation, prompt-cache affinity, and the value of a successful result. Hard-coding a current model ranking into transferable governance would become stale and create provider lock-in.
- Decision: Define `foundation-model-router/v1` as a transport-neutral `RoutingRequest`/`RoutingDecision` contract and ship its executable reference implementation as an opt-in `model-router` capability. The deterministic core applies privacy/remote-provider authority, capability, context, tier, quality, price-freshness, prior-failure, and budget filters before ranking. Ranking minimizes expected cost of success using current input/cached-input/output rates, empirically updated success probability, failure-recovery cost, latency value, switching cost, session/cache affinity, and fallback reach probability. Decisions carry `pricing_epoch` and `valid_until`; every eligible candidate's next rate boundary may invalidate the winner. New models are discovered but begin `UNASSESSED`; ordinary routing requires an operator assessment or a configurable minimum of locally recorded trials. Evaluation planning is explicitly budget- and candidate-capped and can atomically reserve local daily budget, but the router does not invoke a model. Runtime catalogs, outcomes, hashed session keys, reservations, launchers, and snapshots remain outside version control. Provider adapters supply inventory and prices without entering the core. The first adapter combines Ollama Cloud's model-list API with its official pricing page, parses only narrowly identified tables/schedules, hashes normalized pricing into an epoch, reads authentication from the documented environment variable, and leaves the last known catalog untouched on sync failure. CLI, shell-free launcher, expiring snapshot, and newline-delimited stdio MCP all call the same core. Degradation order is MCP, CLI, launcher/snapshot, then portable tier semantics without an invented concrete model or price. Foundation policy and schemas contain no current model names or prices.
- Rationale: A common contract prevents transport adapters from becoming competing routing authorities. Fail-closed freshness protects cost claims. Cost-of-success directly represents the economic objective while preserving quality and safety floors. Local aggregate evidence lets routing improve without storing prompts/responses or depending on a central telemetry service. Keeping invocation outside the router avoids credential duplication and makes the same decision reusable across IDEs, agents, scripts, and providers.
- Alternatives: MCP-only integration was rejected because several clients cannot expose MCP; lowest-token-price routing was rejected because it ignores retries and outcome quality; a durable hard-coded model matrix was rejected because provider catalogs and prices change; automatic live A/B invocation was rejected because it would spend money and transmit task data without a caller-controlled execution boundary; a hosted central router was rejected as the default because it adds availability, privacy, credential, cost, and lock-in concerns; adopting a third-party routing framework was rejected for this reference implementation because the required deterministic decision-only scope is small and dependency-free.
- Consequences: Foundation 1.9 adds a materially richer model-routing contract, five core schemas, an optional dependency-free Python capability, an Ollama Cloud adapter, CLI/launcher/snapshot paths, an MCP stdio adapter, outside-repository atomic state, and regression coverage. Targets may preserve a stronger compatible router or implement the contract in another language. Provider quality profiles and real-task validation remain target-owned. Ollama pricing-page markup is an external compatibility boundary; parse/fetch failure prevents catalog replacement and expired catalogs do not route.
- Affected areas: model/resource policy, dependency/provider handling, runtime state and privacy, schemas, transfer manifest, feature catalog, installer/validator, CLI/MCP/IDE integration, testing, documentation, and upgrade applicability.
