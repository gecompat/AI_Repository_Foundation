# DEC-0016 — Foundation source requires GitHub merge protection; targets receive a recommendation

- Status: Accepted
- Date: 2026-08-25
- Context: Foundation v1.6 introduced semantic object-level registry merge validation and a separate GitHub Actions workflow. Workflow files alone do not make those checks server-side merge requirements. The Foundation source repository was initially observed with `main` unprotected, so a maintainer with sufficient rights could still bypass the checks. At the same time, target repositories may have different Git hosting, administration policy, CI, or stronger controls; Foundation installation must not silently impose repository-admin settings.
- Decision: The AI Repository Foundation source repository requires server-side protection of `main`. The required source-project state uses pull-request-only merge, no mandatory human approval for the current single-maintainer model, strict/up-to-date required checks for `validate` (`Foundation CI`) and `registry-integrity` (`Foundation Artifact Registry`), administrator/bypass enforcement, linear history, no force pushes, and no branch deletion. This source-project requirement is project governance and is not transferred as a mandatory target invariant. When Foundation is installed/upgraded into another project and the GitHub registry capability is relevant, the transfer process and deterministic installer must explicitly surface that GitHub Actions workflows do not automatically become required status checks and recommend enabling suitable branch protection/rulesets. The recommendation is non-blocking for `FOUNDATION_INTEGRITY`, is not applied automatically, and remains a target-project administration choice.
- Rationale: The Foundation should enforce its own semantic merge gates rather than merely document them. Conversely, silently editing another project's repository-administration controls exceeds normal rules transfer and may conflict with established governance or non-GitHub hosting. Explicit recommendation provides the safety benefit without turning Foundation into a GitHub administration authority for targets.
- Alternatives: Rely only on workflow files — rejected because checks can be bypassed on an unprotected branch; make protection a universal Foundation-required target rule — rejected because it is GitHub-specific and may conflict with target governance; automatically configure target branch protection during installation — rejected because it changes repository administration and authorization outside normal file transfer; require human PR approval — not selected because the current requirement is deterministic gate enforcement, not mandatory human review.
- Consequences: `Documentation/Quality/GITHUB_BRANCH_PROTECTION.md` records the Foundation source required state and verification procedure; `tools/github/configure_branch_protection.py` can apply/verify the setting when an Administration-write token is available; direct AI transfer and deterministic installation surface the target recommendation without blocking installation. `WI-0015` may be complete only while GitHub continues to report the required source protection.
- Affected areas: Foundation source GitHub administration, CI merge gates, artifact-registry GitHub capability, installer output, direct AI transfer, source status/handover, repository continuation.
- Evidence: On 2026-08-25 GitHub branch metadata reported `main` as `protected: true`, required-status-check enforcement `everyone`, and required checks `registry-integrity` and `validate`. Manual review of the saved GitHub branch-protection rule confirmed pull-request-only merge, approvals not required, branches required to be up to date, linear history required, bypass disabled, force pushes disabled, and deletion disabled. This supersedes the earlier observation that `main` was unprotected.
