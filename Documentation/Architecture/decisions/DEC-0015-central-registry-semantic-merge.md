# DEC-0015 — Central registry uses derived allocation and object-level merge gates

- Status: Accepted
- Date: 2026-08-25
- Context: The Foundation v1 registration reference profile separates allocator state from complete artifact records and persists `next_sequence` plus `registry_revision`. FolioTone usage and review of repository-native workflows showed that a central structured JSON authority is simpler to query, validate, project into human-readable views, and consume from local tooling. In a central registry, `next_sequence` is deterministic derived state. At the same time, multiple pull requests may modify the same JSON file, and Git's line-oriented merge can either report unnecessary text conflicts or produce syntactically valid JSON whose object semantics were never reviewed. Early detection against other open pull requests is also valuable because it allows human/AI workers to correct reference collisions before final integration.
- Decision: Introduce `foundation-artifact-registry/v2` as the Foundation default profile when a project chooses a repository-native JSON Registration Authority. Store complete registered records in one central `artifacts` object keyed by canonical human reference. Do not persist redundant `human_ref` fields in those records. Do not persist `next_sequence`; derive the next candidate as the maximum existing canonical sequence for the prefix plus one, including live reservations when the authority defines them. For Git-native v2 registries, do not persist a second mutable global `registry_revision`; Git commit/blob state is the concurrency token. Keep `foundation-artifact-registry/v1` as a compatible legacy profile and never auto-migrate an existing project authority. A central registry merge is a recursive object/property-level three-way merge over `BASE`, current target `MAIN`, and PR `HEAD`: single-sided changes are applied, identical concurrent changes are accepted, independent object-property changes may combine, and divergent changes to the same scalar/list/property or concurrent different additions of the same canonical key are conflicts. Lists are atomic unless a narrower project contract defines safe element semantics. After structural merge, run cross-record semantic integrity validation. For GitHub workflows, additionally simulate Git's actual textual merge of the registry and require its parsed JSON result to equal the object-level semantic result; a textual conflict or semantic mismatch blocks. Run an early cross-PR preflight for duplicate new human references, duplicate UIDs, alias collisions, and overlapping edits. Allow generated backlog/status/roadmap projections, but keep the central registry as the canonical state. Provide the GitHub implementation only as an optional capability; the normative contract remains language- and platform-neutral.
- Rationale: Central state removes registry-to-artifact synchronization failure modes and makes schema/query/local tooling straightforward. Derived `MAX+1` allocation avoids an unnecessary second truth and does not weaken concurrency compared with a persisted counter. Object-level three-way merge preserves the benefits of central structured state without trusting Git's line heuristics. Comparing the actual Git result closes the gap where Git could silently combine lines into a structurally different but valid JSON object. Early open-PR inspection shifts many collisions from merge time to PR creation/update time.
- Alternatives: Keep split artifact JSON files plus a central allocation registry — rejected as the default because it requires joins and cross-file consistency while new-reference allocation remains a central hotspot anyway; keep `next_sequence` as a cache — rejected because it is cheap deterministic derived state and can drift from the artifact keys; rely on Git's normal line merge plus post-merge schema validation — rejected because schema-valid JSON can still represent the wrong semantic merge; require a central database/service for all projects — rejected because it adds infrastructure that many repository-scale projects do not need; automatically resolve divergent changes to the same property — rejected because the correct semantic value is not mechanically knowable.
- Consequences: Foundation v1.6 adds the v2 schema, central-registry policy, optional GitHub semantic-merge/preflight capability, generated-view checks, and deterministic tests. The Foundation source repository migrates its own planning authority to v2 and generates `.ai/BACKLOG.md` from `.ai/identity/registry.json`. Projects with an existing v1/split/service authority remain compatible unless they explicitly select migration. GitHub workflow files provide checks, but repository administration must still configure the relevant status checks/ruleset as required if hard server-side merge enforcement is desired.
- Affected areas: artifact registration, persistent planning identity, Foundation source planning, Git/GitHub workflows, CI validation, semantic merge, transfer manifest, feature catalog, generated documentation, project upgrade decisions.
- Evidence: implementation head `1bd2a9bb0a487780e2d12401ae2747cadef3f6d3` passed Foundation CI run `32837531482` and Foundation Artifact Registry run `32837531385`; the registry workflow passed head validation, generated-backlog verification, cross-PR preflight, object-level three-way merge, and Git-text-merge equivalence.
